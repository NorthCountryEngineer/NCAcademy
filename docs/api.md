# API and data contracts

Verified Core identities resolve through an explicit tenant/issuer/subject binding to stable local owner IDs. Login and current-session checks validate the bound target's tenant, user kind, enabled state and subject. Authority migration has no public API; use the [operator backfill](core-issuer-migration.md). Runtime binding privileges permit SELECT/INSERT and forbid UPDATE/DELETE/TRUNCATE.

The machine-readable [OpenAPI reference](reference/openapi.json) captures the typed request schemas; regenerate it from the current application after endpoint/schema changes. The API lives under `/api`; browser requests use the same origin and server-side session cookie. Browser mutations require both the canonical `Origin` and the per-session `X-CSRF-Token`. Approved agent requests use their own Core Bearer identity and live backend introspection, not a human cookie or CSRF token. Mixed or malformed credentials fail closed. Error bodies omit submitted values so credential-validation failures do not echo secrets.

Production human Core bindings validate issuer, canonical organization/service/deployment UUIDs, environment, public issuing client, service audience, bearer type, scope, expiry and subject. `academy-use` admits ordinary service access; `academy-school` permits scoped school administration, `academy-teach` teaching, and `academy-audit` Teacher replay when exact school/class membership also allows it. Human School administrators may review their own school through `academy-school`. Core's reserved `admin` grants tenant-wide application administration in addition to mandatory `academy-use`. The first valid Core sign-in creates the stable local user record but does not confer school/class access by itself. Role labels, email addresses and browser state confer no authority.

Agent claims use a separate Core contract at `/api/platform/v1/agent-credentials/introspect/`. Academy's scoped backend workload credential authenticates that request. Exact issuer/audience/organization, nonhuman subject/account, binding/consumer, environment/task, expiry and operation permissions must match an active approved local placement. Core checks registered resource policy; local school/class scope remains mandatory. See [permissions](permissions.md) for the complete role and agent contract.

Storage is dedicated PostgreSQL in production. Curriculum, enrollment, work, integration and tutor-operation records retain tenant/parent/owner identity. Audit and submission immutability is also enforced with database triggers, while independently retained checkpoints protect the audit head outside the database's administrative trust boundary. The migration is explicit; readiness and callbacks do not create schema. Migration uses the database owner; the API's separate restricted login can append audit events and update the audit head, but cannot rewrite/delete/truncate events or change schema. Independent archive writes and KMS signing use operator authority outside the API.

Provider calls receive an immutable bounded prompt/policy/connection snapshot with an encrypted credential resolved server-side. The visible selection and normalized usage are stored for instructor review; hidden reasoning and vendor metadata are discarded. Assignment output releases only an allowed instructor-authored selection. Lesson Q&A accepts only a strict admitted `document_id` selection and renders the exact reviewed public passage with citations and fixed style text. The protocol excludes tool use, arbitrary model prose, autonomous assignment completion and automatic inference retries.

`CourseInput.curriculum` optionally specifies `state`, `subject`, `grades`, `academic_year` and `standards_version`. Omitting it from an existing course edit preserves the prior value; explicit null clears it and invalidates the old corpus. Course creation/configuration and teacher planning assignment build snapshots automatically. `TutorInput.teacher_profile_id` optionally selects an eligible approved AI profile for that class. The profile/corpus/quoted retrieval context is snapshotted, contributes to the reservation and is revalidated before the provider call and before release. A teacher change cannot reuse an earlier idempotency key. See [teachers and standards](teachers-and-standards.md) for workflow and limits.

Teacher AI profiles have an optional `tutor_model` with `connection_id`, `model`, `max_turns`, `max_input_chars`, `max_output_tokens` and `max_total_tokens`. The human approves exact same-school connection/model policy together with the profile/corpora. `max_turns` and `max_total_tokens` are daily per student/course across every teacher profile; saved server-derived `budget_day` uses UTC. Pending sends block across dates. Requests cannot select/reset their day or quota. Course-level `lesson_turn` history uses a stable tenant/course/student session ID; current authorized reviewers can replay/export its full evidence through the existing audit routes, with `session_kind: "lesson"`.

Manager profile responses include server-derived `approval_current`. Matching metadata versions alone do not establish current teaching context: the exact planned-course set, current curriculum and each ready approved corpus reference must also match the immutable teacher revision. Approving a new corpus leaves this flag false until the human approves the teacher profile again. Reapproval accepts the current `expected_version` without requiring a redundant metadata edit.

Managed AI profiles grant no Core API role. Their approved planned classes admit bounded Lesson Q&A and explicitly approved private lesson curation to enrolled students under the global live-model gate. Bound profiles additionally require actual class teaching authority, local placement, agent admission and fresh backend-workload authorization at Core's `/api/platform/v1/agent-bindings/authorize/`. No credential is minted, borrowed from a human or returned to the browser. Missing/revoked Core authority fails closed without managed-mode fallback.

Private curation adds strict teacher-policy opt-ins `allow_lesson_curation` and `allow_assignment_images` (both false by default), plus `curation_max_output_tokens` (200–1200, default 700). Image permission requires curation permission and manual image-capability review. The daily `max_total_tokens` upper bound is 1,000,000 to allow conservative encoded-image reservations; its default remains 20,000. Existing approved policies remain valid with curation off until explicitly edited/reapproved.

`CuratedLessonInput` accepts `teacher_profile_id`, `message`, up to two `{name,data_url}` images, strict `image_use_confirmed`, `preferences` (`pace`, unique `read`/`visual`/`listen` formats with reading required) and `idempotency_key`. At least a description or image is required. The exact curation POST alone admits up to 400,000 actual/declarative request bytes; ordinary API routes remain at 150,000. Student responses return safe lesson bundles and image metadata/scoped URLs only. Full replay strips encrypted attachments, keeps wire-request hashes/media evidence and records student reflections. See [student-curated lessons](student-curated-lessons.md) for image bounds, protocol and retention.

## External media review

Human school managers use `GET/PUT /api/schools/{school_id}/audit-agent` and `GET /api/schools/{school_id}/external-review`. Assigned course staff use `GET/POST /api/courses/{course_id}/external-resources`, `POST .../import-corpus`, and `GET/PUT /api/external-resources/{resource_id}`. Explicit review uses `POST .../{resource_id}/review` with expected version and school-scoped idempotency key. Human publication uses `POST .../approve` with exact version, review ID, source hash and required YouTube attestations. Revocation uses `POST .../revoke`. `POST .../playback` checks current authorization and public metadata before returning a server-generated privacy-enhanced embed. Student reads omit pending material and private transcript/model evidence. Automatic clean nonvideo publication is governed by the assigned administrator policy. See [external media review](external-media-review.md) and the checked [OpenAPI reference](reference/openapi.json) for exact inputs.
