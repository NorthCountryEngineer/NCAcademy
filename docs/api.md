# API and data contracts

## Administrative workspace

`/api/schools/{school_id}/administration` requires a current human Admin/School role for the exact school on every read and write. The administrative page and sidebar navigation remain application-Admin features. Profiles are job definitions and never create Core identities, roles or grants.

| Route below the workspace base | Operation |
| --- | --- |
| `GET /` or `GET /catalog` | Integration setup descriptors, built-in skills and current execution capabilities. |
| `GET/POST /agents`, `GET/PUT /agents/{id}` | List, create, read or replace a declarative administrative profile. |
| `GET/POST /skills`, `GET/PUT /skills/{id}` | Manage custom definitions over registered fixed actions. Built-ins cannot be replaced. |
| `GET /{agents\|skills}/{id}/versions` | Read retained immutable configuration revisions. |
| `POST /{agents\|skills}/{id}/{archive\|restore}` | Change lifecycle with the exact expected version. |
| `POST /agents/{id}/runs` | Explicit launch with `expected_version` and a bounded opaque `idempotency_key`. |
| `GET /runs/{id}` | Read scoped steps, status and the retained advisory result. |
| `GET /activity` | Bounded school-scoped operational metadata, with kind/status filtering and offset/limit pagination. |

Create uses `expected_version: 0`; edits and lifecycle changes must match the current version. Every saved configuration appends a protected revision. Only `readiness.inspect`, `curriculum.plan` and `model.review` effects are registered. Local review has no provider call. Model review requires its registered skill, a selected enabled school model, explicitly confirmed recent input/output prices, run budget and input/output/daily limits. The deployment gate remains authoritative.

Accepted model work commits a send marker before external I/O, rechecks current authority/configuration and records a sealed outcome before release. Reusing a launch key reads the prior accepted run; it never resends an uncertain request. Reports cannot execute tools, approve/publish materials, change policy or read learner content. Legacy activity projection reads only allowlisted structural metadata from stored JSON and does not decrypt student sessions. Existing session-audit APIs remain separate. See [administrative settings](administrative-settings.md) and the generated [OpenAPI reference](reference/openapi.json).

## Game Studio and class practice games

These routes use the existing school/class session authority. Local student accounts stay local; the integration reads public Game Studio data without forwarding credentials or student details.

| Method and route | Contract |
| --- | --- |
| `GET /api/schools/{school_id}/game-studio` | Current connection and runtime contract; defaults disabled. Human school staff only. |
| `PUT /api/schools/{school_id}/game-studio` | Human Admin/School saves origins, host ID and enabled state with `expected_version`; no network request. |
| `POST /api/schools/{school_id}/game-studio/verify` | Explicit public descriptor check with `expected_version`; creator navigation and optional host-return readiness are separate. |
| `GET /api/schools/{school_id}/game-studio/catalog` | One bounded public catalog page; optional opaque `cursor`, no automatic all-pages fetch. |
| `GET /api/courses/{course_id}/games` | Staff drafts or currently approved student metadata; no student game definition in this response. |
| `POST /api/courses/{course_id}/games` | Prepare a draft from exact `game_id`, `published_revision`, `spec_sha256`, `learning_objective`, `lesson_label` and `idempotency_key`; refetch and validate server-side. |
| `GET /api/courses/{course_id}/games/{resource_id}` | Authorized staff preview of the retained package. |
| `POST /api/courses/{course_id}/games/{resource_id}/approve` | Human Admin/School attests `reviewed: true`, all exact `reviewed_level_ids` and `expected_version`. |
| `POST /api/courses/{course_id}/games/{resource_id}/revoke` | Human Admin/School revocation with `expected_version`; prior package and approval evidence remain immutable. |
| `POST /api/courses/{course_id}/games/{resource_id}/play` | Empty object body; fresh upstream edition/hash and current class/session/approval checks before audited local snapshot delivery. |

GameSpec versions 1 and 2 are data-only fixed-engine inputs. Unknown fields, executable content and unsupported mechanics are rejected. Human approval is bound to the package, school connection revision, class context and `game-studio-data-v1` implementation digest. An upstream update or withdrawal blocks a new play request; it cannot silently replace the approved definition. Gameplay has no account federation, public scores, private student export or grade submission. See [the integration and extension plan](game-studio.md).

## Course and teaching contracts

Course create/update accepts an optional `teacher_profile_ids` list for the school's reusable human/AI teaching profiles, independently of `teacher_id` (the existing responsible account). Omitting the profile list preserves assignments; an explicit empty list removes this class's profile assignments. Explicit null, duplicate IDs and invalid ID shapes are rejected with 422. Editors may send `expected_teacher_profile_ids` with an explicit selection; a changed current team returns 409 and rolls back the entire course update. Staff course responses include planned `teacher_profile_ids` and minimal `assigned_teacher_profiles` labels even before teaching readiness; students receive only existing approved teaching cards. Selection does not grant Core access or approve teaching materials. Only human School/Admin users can change the list. Same-school active-profile validation and all assignment/workflow changes are atomic. See [course teacher assignment](teachers-and-standards.md).


Teacher execution settings: `GET/PUT /api/schools/{school_id}/teachers/{profile_id}/models`, `POST .../models/approve` and `POST .../models/preview`. Draft/approval writes require human School/Admin authority and optimistic expected versions. The primary, separate activity limits, candidate pool and preview rules are independent of profile metadata. See [the contract and rollout plan](teacher-models.md).

`GET /api/course-catalog` exposes all 2,030 official NYSED 2026–2027 course entries to currently authorized class-creation staff/agents. Search, subject/level filters, optional Regents-only discovery and bounded pagination do not depend on school curriculum or AI corpus readiness. Course create/update accepts an optional four-field exact-source `course_catalog` selector; the server stores official metadata and provenance. `course_catalog: null` and `curriculum: null` create an independent custom class, even in a NYS-curriculum school. Omitted update fields preserve existing bindings; explicit null clears them. Agent proposals are revalidated on human publication. See [the complete course contract](ny-course-catalog.md).

Schema 11 adds the separately approved generative Homework Help surface and transactional metadata outbox. The [Homework Help AI route table](homework-help.md#ai-api) covers configuration/approval, own paginated conversations, automatic topic/AI-teacher routing with direct triage fallback, photos, full school review and class-limited Teacher/agent review. `GET /api/homework-help/audit-delivery?school_id=…` exposes authorized metadata-only delivery counts/timestamps; global Admin may omit the school filter. It audits access and does not establish archive freshness. Existing `/me/feedback` also accepts a currently released own AI message ID. Course enrollment is optional for this chat. Public approved school AI personas may help outside their classes under the version-2 school approval; protected coursework and class-only audit still require existing enrollment/authority. Configuration descriptors expose `boundary_version`, `reapproval_required` and `unavailable_reason`; `use_school_teacher_personas` controls optional teacher handoff. The older Homework routes remain separate and keep their selection-only contract.

The API has no public dispatcher-control or archive-key endpoint. Outbox events are appended in the audit transaction; a dedicated worker updates state and appends immutable receipts through restricted database grants. See [the exact Core pipeline/worker contract](audit-delivery.md). The generated OpenAPI document records new typed request schemas and forbids extra input fields.

Local family accounts add username/password sign-in, own password change, Admin-only profile/password/enrollment/lifecycle routes and a limited own-family progress endpoint. They are explicitly excluded from Core identity bindings, resource authorization and Google/Core Chat integration. [The account contract](family-accounts.md#api) documents routes, encryption, version checks, parent eligibility and test procedures. Schema 10 protects encrypted immutable family events. Audit ciphertext remains the hashed original; authorized replay may include a separate decrypted `private_payload`.

Verified Core identities resolve through an explicit tenant/issuer/subject binding to stable local owner IDs. Login and current-session checks validate the bound target's tenant, user kind, enabled state and subject. Authority migration has no public API; use the [operator backfill](core-issuer-migration.md). Runtime binding privileges permit SELECT/INSERT and forbid UPDATE/DELETE/TRUNCATE.

The machine-readable [OpenAPI reference](reference/openapi.json) captures the typed request schemas; regenerate it from the current application after endpoint/schema changes. The API lives under `/api`; browser requests use the same origin and server-side session cookie. Browser mutations require both the canonical `Origin` and the per-session `X-CSRF-Token`. Approved agent requests use their own Core Bearer identity and live backend introspection, not a human cookie or CSRF token. Mixed or malformed credentials fail closed. Error bodies omit submitted values so credential-validation failures do not echo secrets.

Production human Core bindings validate issuer, canonical organization/service/deployment UUIDs, environment, public issuing client, service audience, bearer type, scope, expiry and subject. `academy-use` admits ordinary service access; `academy-school` permits scoped school administration, `academy-teach` teaching, and `academy-audit` Teacher replay when exact school/class membership also allows it. Human School administrators may review their own school through `academy-school`. Core's reserved `admin` grants tenant-wide application administration in addition to mandatory `academy-use`. The first valid Core sign-in creates the stable local user record but does not confer school/class access by itself. Role labels, email addresses and browser state confer no authority.

Agent claims use a separate Core contract at `/api/platform/v1/agent-credentials/introspect/`. Academy's scoped backend workload credential authenticates that request. Exact issuer/audience/organization, nonhuman subject/account, binding/consumer, environment/task, expiry and operation permissions must match an active approved local placement. Core checks registered resource policy; local school/class scope remains mandatory. See [permissions](permissions.md) for the complete role and agent contract.

Storage is dedicated PostgreSQL in production. Curriculum, enrollment, work, integration and tutor-operation records retain tenant/parent/owner identity. Audit and submission immutability is also enforced with database triggers, while independently retained checkpoints protect the audit head outside the database's administrative trust boundary. The migration is explicit; readiness and callbacks do not create schema. Migration uses the database owner; the API's separate restricted login can append audit events and update the audit head, but cannot rewrite/delete/truncate events or change schema. Independent archive writes and KMS signing use operator authority outside the API.

Google Classroom uses personal server-held OAuth under a separate default-off gate. The three fixed scopes permit student course/work reads; there are no write/submission/Drive/roster scopes. Google IDs and credentials remain in mutable encrypted account/link envelopes, with irreversible keyed request fingerprints for idempotency. Current Google active-student enrollment is established within at most ten bounded pages before mapped work reads. Imported content never enters models, teaching corpora, ordinary audit exports or Homework history automatically. Schema 9 protects safe local events/operation receipts. See [the companion](google-classroom.md) and [official-source contract](google-classroom-contract.md).

Group chat uses the existing browser CSRF/agent authority boundary. Inputs forbid upstream actor, installation, participant and room overrides. Group creation pins school, optional course, visibility, join policy and idempotency key. Messages pin text, optional admitted reply UUID and idempotency key; history accepts `after` 0–2^63−1 and `limit` 1–100. Directory responses explicitly mark truncation. Schema 8 protects local command/delivery/member/publication evidence. Core message storage is application-attributed; actual authors and approval are retained in NCAcademy. See [groups](group-chat.md) and [the exact Core contract](core-chat-contract.md).

Student intake answers are strict integers from 0 to 4 for `reading`, `diagrams`, `video`, `audio`, `pace`, `detail`, `encouragement`, `question_frequency` and `structure`. New tutoring admissions require complete intake; existing terminal history and idempotent requests retain their original evidence. Effective 0–100 weights are computed from immutable personal baseline and scoped style feedback, then pinned and revalidated before send/release. Accuracy ratings flag review only. The schema-5 migration protects preference/feedback records. No route can edit another student's settings, modify a teacher's approved shared profile or authorize new media. See [preferences](student-learning-preferences.md) for reset, adaptation and feedback limits.

Persistent external archiving uses a separate read-only database worker and S3-compatible storage identity. It exposes no public archive-management, browser-credential or raw storage URL endpoint. Owner recovery is an offline verified export under separate authority; see [session archiving](session-archive.md).

Provider calls receive an immutable bounded prompt/policy/connection snapshot with an encrypted credential resolved server-side. The visible selection and normalized usage are stored for instructor review; hidden reasoning and vendor metadata are discarded. Assignment output releases only an allowed instructor-authored selection. Lesson Q&A accepts only a strict admitted `document_id` selection and renders the exact reviewed public passage with citations and fixed style text. The protocol excludes tool use, arbitrary model prose, autonomous assignment completion and automatic inference retries.

`CourseInput.curriculum` optionally specifies `state`, `subject`, `grades`, `academic_year` and `standards_version`. Omitting it from an existing course edit preserves the prior value; explicit null clears it and invalidates the old corpus. Course creation/configuration and teacher planning assignment build snapshots automatically. `TutorInput.teacher_profile_id` optionally selects an eligible approved AI profile for that class. The profile/corpus/quoted retrieval context is snapshotted, contributes to the reservation and is revalidated before the provider call and before release. A teacher change cannot reuse an earlier idempotency key. See [teachers and standards](teachers-and-standards.md) for workflow and limits.

Teacher AI profiles have an optional `tutor_model` with `connection_id`, `model`, `max_turns`, `max_input_chars`, `max_output_tokens` and `max_total_tokens`. The human approves exact same-school connection/model policy together with the profile/corpora. `max_turns` and `max_total_tokens` are daily per student/course across every teacher profile; saved server-derived `budget_day` uses UTC. Pending sends block across dates. Requests cannot select/reset their day or quota. Course-level `lesson_turn` history uses a stable tenant/course/student session ID; current authorized reviewers can replay/export its full evidence through the existing audit routes, with `session_kind: "lesson"`.

Manager profile responses include server-derived `approval_current`. Matching metadata versions alone do not establish current profile approval: the exact planned-course set, current curriculum and each current corpus reference must also match the immutable teacher revision. A human may approve a profile with pending or unsupported class corpora; this records their current references without approving teaching materials. Class tutoring separately requires a current ready approved corpus, and `activation.managed_lesson_configured` remains false while assigned materials are unready. Approving a new corpus leaves the old profile's flag false until the human approves the profile again. Reapproval accepts the current `expected_version` without requiring a redundant metadata edit.

Managed AI profiles grant no Core API role. Their approved planned classes admit bounded Lesson Q&A and explicitly approved private lesson curation to enrolled students under the global live-model gate. Bound profiles additionally require actual class teaching authority, local placement, agent admission and fresh backend-workload authorization at Core's `/api/platform/v1/agent-bindings/authorize/`. No credential is minted, borrowed from a human or returned to the browser. Missing/revoked Core authority fails closed without managed-mode fallback.

Private curation adds strict teacher-policy opt-ins `allow_lesson_curation` and `allow_assignment_images` (both false by default), plus `curation_max_output_tokens` (200–1200, default 700). Image permission requires curation permission and manual image-capability review. The daily `max_total_tokens` upper bound is 1,000,000 to allow conservative encoded-image reservations; its default remains 20,000. Existing approved policies remain valid with curation off until explicitly edited/reapproved.

`CuratedLessonInput` accepts `teacher_profile_id`, `message`, up to two `{name,data_url}` images, strict `image_use_confirmed`, `preferences` (`pace`, unique `read`/`visual`/`listen` formats with reading required) and `idempotency_key`. At least a description or image is required. The exact curation POST alone admits up to 400,000 actual/declarative request bytes; ordinary API routes remain at 150,000. Student responses return safe lesson bundles and image metadata/scoped URLs only. Full replay strips encrypted attachments, keeps wire-request hashes/media evidence and records student reflections. See [student-curated lessons](student-curated-lessons.md) for image bounds, protocol and retention.

## Homework Help and voice

`/api/homework-help` provides the enrolled routing catalog and own conversation index. Student mutations create immutable sessions/messages; an explicit same-key resume can recover a request interrupted before lesson admission. Photo-aware messages alone accept 400,000 HTTP bytes. School/Admin humans discover and review conversations through separate audited catalog/review endpoints, including pre-triage evidence. See [the complete Homework contract](homework-help.md).

`/api/admin/voice` exposes scoped status/configuration with write-only key replacement. Course voice routes maintain personal stock-voice choices, accept consentful bounded WAV transcription and synthesize only a server-derived owned released reply. The transcription route alone has a 4,300,000-byte HTTP cap; real PCM remains capped at 3 MiB/30 seconds. Receipt lookup never resends uncertain work. Schema 6 preserves immutable Homework/voice evidence. See [the complete voice contract](homework-voice.md).


## Student avatars and moderation

All routes below begin `/api/schools/{school_id}`. Avatar images, state and decision evidence use the independent family PII key for every Student identity. Student routes enforce current enrollment in the school; review and policy routes require a current human Admin or School administrator. Teachers, agents and parents have no review or private-image authority.

| Route | Contract |
| --- | --- |
| `GET/PUT /avatar-policy` | Read or save a versioned school image-scanner draft, exact integrated model, image-processing permission and risk thresholds. |
| `POST /avatar-policy/approve` | Human approval of the exact immutable `revision_id`. Configuration changes require fresh approval and student consent. |
| `GET/POST /me/avatar`, `DELETE /me/avatar` | Read status, upload a bounded normalized image with optimistic version/idempotency controls, or remove the current display pointer. Upload consent binds `expected_policy_approval_id`; no approval means private manual review. |
| `POST /me/avatar/{avatar_id}/scan` | Explicitly admit a retained upload to the exact approved scanner. Pending/uncertain sends cannot be retried automatically. |
| `GET /avatars/{avatar_id}/image` | Private JPEG for the current approved avatar only; no public or unreviewed image URLs. |
| `GET /avatar-reviews`, `GET /avatar-reviews/{avatar_id}` | Metadata-only queue and retained admission, scanner, threshold, policy, model and human decision evidence. |
| `POST /avatar-reviews/{avatar_id}/reveal` | Explicit acknowledged sensitive-image reveal, with `expected_version`; never a queue thumbnail. |
| `POST /avatar-reviews/{avatar_id}/decision` | Human approve/reject of the exact current version with a reason of at least ten characters. |
| `POST /avatar-reviews/{avatar_id}/close-scan` | Explicitly close an interrupted scan before manual review, retaining the uncertain send and any late report. |

Sexual findings quarantine the image; violence and other inappropriate-content findings require human review. Unscanned, invalid and uncertain results remain hidden. A late unsafe report re-hides that exact candidate even after an earlier human approval, preserving the earlier decision and requiring renewed review. The API records fixed category/rule evidence, not provider free text or hidden chain of thought. See [student avatars](student-avatars.md) and the [typed OpenAPI reference](reference/openapi.json) for exact inputs, privacy boundaries and limits.
