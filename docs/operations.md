# Operations and recovery

Local student/parent administration, grade/year history, password replacement and PII key recovery have a dedicated [operations and test guide](family-accounts.md). Staff retain Core authority; local family accounts are never created upstream. A parent's last qualifying child leaving enrollment revokes its sessions. Back up the independent PII key alongside separately encrypted database backups; do not swap keys in place or rely on the archive key to decrypt private account/session payloads. Historical Core/demo plaintext is preserved, not silently migrated.

## Local installation

Run `python3 scripts/setup_local.py` once to create ignored local secrets, then `docker compose up --build -d`. Open `http://localhost:8090`. Compose uses project `ncacademy-local`, dedicated PostgreSQL storage and loopback-only frontend port 8090. The API/database are not published to the host. Other local Proposal Studio/Core containers and volumes are not part of this project.

Inspect status with `docker compose ps` and health with `docker compose exec api python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/api/ready').status)"`. View service logs with `docker compose logs --tail 100 api`. Keep student/provider payloads out of logs. `docker compose down` stops the local service while retaining its database. Removing the named database volume is a deliberate destructive reset, not an upgrade step.

Local roles are synthetic demonstration identities selected at sign-in. Courses, policies and work you create in that mode are still local records; never put real student records into a source screenshot or archive.

## Initial production access

Use `https://ncacademy.app`; its `/api` requests proxy to the protected backend at `https://api.ncacademy.app`. Identity uses `https://core.nnytech.ai`. Grant the owner both Core `admin` and `academy-use` plus production environment access. A valid first sign-in creates the stable local app user; it does not grant a school membership. No production demo users are seeded. Preserve existing owner IDs and both reviewed issuer aliases during upgrades.

Keep live models disabled and issue no student grants until independent retained audit verification and access acceptance are complete. API readiness establishes schema/storage availability only. Database owner credentials belong solely to migration; the API receives a restricted runtime login and has no AWS task role. The migration bootstrap inputs are `ACADEMY_RUNTIME_DB_USERNAME` and `ACADEMY_RUNTIME_DB_PASSWORD`, injected from the runtime database secret and never printed.

## Instructor workflow

An Admin creates a school and assigns human School administrators. School administrators assign Teacher/Student memberships and school resources; live Core permissions remain necessary. Select the intended school, create or open an assigned class, enroll its students, add assignments and choose a module grouping. Write the assignment prompt and a small vetted hint/question bank. Leave assistance off for independent assessments; select curated assistance for deterministic stored hints or Socratic selection when an approved provider is enabled. Students write/save their attempts and submit their own work. Human and approved agent Teachers review immutable submissions; session replay additionally requires the current Teacher audit grant. Recorded saved-draft versions remain reviewable evidence; student write/draft access remains owner-only.

Review assistance chronologically, comparing attempt snapshots and released hints with the final submitted version. Review blocks/errors as well as successful hints. Do not interpret a provider selection or service transcript as proof of the student's unseen reasoning.

When replacing a teacher, transfer class ownership and explicitly remove the former teacher's enrollment if their access should end. Ownership transfer preserves existing teaching assignments; it does not silently revoke them. Human School/Admin controls teacher assignments. Revoking a school membership or agent placement denies all classes in that scope on the next request.

## Administrator workflow

Google Classroom connections belong to students. After the dedicated operator/Google setup, students open a class's Google Classroom tab to connect, link an active Google course and explicitly load assignments. Native editing and turn-in stay in Google. School staff cannot use a student's token or view imported private coursework through administrative replay. Their normal NCAcademy Homework questions remain reviewable under existing permissions.

For an expired/revoked/uncertain credential or changed OAuth client/callback configuration, reconnect explicitly; never reset a pending refresh marker for replay. Disconnect clears local tokens/mappings before revocation and preserves an unknown remote result when necessary. A separate own-connections disclosure and API cleanup path works after school/class removal. Keep the Google project dedicated because remote revocation may invalidate other clients/scopes in the same project. See [Classroom recovery](google-classroom.md).

After creating a school, continue to School setup to choose its curriculum and grade/year courses, review the draft source plan, create selected classes and onboard the teaching team. Add or replace the school logo and custom metadata in School configuration. Setup can be resumed later from School settings. Inspect Knowledge workflows for the actual class/corpus and teacher-assignment results, then open each class to review and approve its corpus before approving the teacher's current configuration. A no-curriculum school can use manually created classes; custom curriculum records intent while ingestion is deferred. See [school setup](school-onboarding.md).

Use Administrative settings for school/member status, shared resources, named model connections, enabled model choices and application/audit configuration status. School administrators see only the schools they manage. Enter a replacement key only when replacing it, or explicitly clear the saved key. The API never returns saved secrets. Configure authoritative production permissions in Core; local school membership and course enrollment are additional application boundaries. Changing client/tenant/domain bindings requires an explicit registration/release process.

## Agent teacher approval

For ordinary AI profile onboarding, use Teachers rather than the advanced Core placement form. Save the shared portrait/name/biography and behavior, assign classes, review/approve each current public course corpus, configure a named enabled model policy and approve the exact profile. Course, source, model-policy or profile changes can require renewed review. The currentness indicator includes each assigned class context; approving a new corpus does not silently approve its use by an old teacher revision. Managed personas receive no account/credential or Teacher API permissions. Keep live traffic off until provider and student-admission acceptance. See [the teacher guide](teachers-and-standards.md).

Private student curation and assignment images are separate explicit teacher-policy options, default off. Verify the approved model's image protocol/processing terms, review the public sources and set a daily reservation limit that includes encoded images before approval. No live probe runs on save. Retained normalized photos are encrypted with the stable vault bootstrap and included in the database recovery boundary; session/audit JSON contains hashes and protected endpoints rather than binary images. Preserve the bootstrap, encrypted database and independent audit checkpoints together through normal controlled backup/restore. Student photos never become shared course resources automatically. See [student-curated lessons](student-curated-lessons.md).

Create and approve the agent account and consuming application/environment binding in Core, with `academy-use` and `academy-teach`, applicable resource/tag grants, and an expiring task when required. Core task `service_resources` lists contain registered resource UUIDs, not Academy's external IDs. MFA-only tags cannot be satisfied by an agent. Keep the human owner-only policy until a reviewed agent policy explicitly permits workloads.

Configure Academy's server-side Core workload credential through the approved runtime secret and explicitly enable agent teachers only after transport and permission acceptance. `ALLOW_AGENT_TEACHERS` and `ALLOW_LIVE_MODELS` are independent operator switches: agent authentication does not enable models, and model enablement does not admit agents. Missing credentials or disabled agent admission deny Bearer requests. Do not put the workload token in a frontend environment variable, application manifest, prompt, log, school resource or source archive. Migration tasks must not receive it.

A human School/Admin records the exact local placement and class assignments. Agents use their own short-lived Core token; they cannot exchange other agents' credentials or borrow browser sessions. Assignment changes and freeform review feedback remain pending until a human School/Admin approves their exact content. Confirm the proposed school/class, content version and effect on student-visible guidance before approval. Agent teaching does not permit student impersonation, submitted-work edits, school-role grants, secret management or tenant-audit export. Assigned-class assistance replay requires current `academy-audit` and preserves the existing recorded evidence, including saved-draft versions and attempt snapshots. It never grants direct student-draft access or student write authority. See [permissions](permissions.md).

If an approval returns a target/placement conflict, retain the old proposal as evidence and request a fresh one. The server pins the original target and placement authority; it will not publish that old proposal over a later edit, changed binding or revoked class assignment.

For the additive school upgrade, capture a backup and retained audit checkpoint, stop admission, explicitly review the existing Core package/installation's four-permission identity contract, run the reviewed owner-only migration, verify stable identity/record/submission/audit hashes and restart the compatible API image. Existing resources receive explicit Default-school scope. Repeated migration must not create duplicate schools/memberships or reset later grants. Keep existing Core registration IDs and tag/grant policies; do not recreate the installation to resolve a contract mismatch. Rollback requires a schema-compatible image; the old tenant-wide permission implementation is not a safe substitute for school isolation.

## Audit export verification

An Admin exports the complete tenant audit chain through the authenticated admin export endpoint. School/session views contain selected events and are marked partial; they cannot prove continuity of the entire tenant chain independently or disclose other schools' records. Store exports outside the source tree in restricted operator storage.

```sh
python3 scripts/verify_audit.py /PRIVATE_OPERATOR_PATH/audit-export.json
python3 scripts/verify_audit.py /PRIVATE_OPERATOR_PATH/audit-export.json \
  --checkpoint /INDEPENDENT_RETAINED_PATH/trusted-checkpoint.json
```

The verifier checkpoint has `tenant_id`, `sequence` and `digest`, obtained from a separate trusted retention boundary. Without it, the verifier reports internal consistency only. It detects changed event contents/order, tenant mismatches and a truncated chain relative to the trusted head. The CLI does not verify KMS signatures; authenticate the independently retained signed checkpoint first, then supply its trusted head to this verifier.

For an operator checkpoint, preserve the exact exported bytes and SHA256, tenant/head, UTC timestamp, KMS signing key and algorithm metadata, signature and retained S3 object versions. Verify the signature and exported-byte checksum before chain verification. Retain export and signed checkpoint in the independent Object Lock archive using separate operator authority. The API cannot write the archive or sign its own head. The separate [S3-compatible archive worker](session-archive.md) adds an automated path with independently managed encryption/signing keys; configure and verify it explicitly. Establish a documented cadence, missed-checkpoint alert and recovery owner before student admission. Archive access must be logged independently as well as through application export events.

Exercise changed event content and deleted-tail detection against the retained head, then restore a synthetic export/backup into an isolated database and verify it. An initial signed schema checkpoint is useful deployment evidence but does not cover later student sessions.

## Monitoring and recovery

Use Groups to inspect the current school directory and required class conversations. The API checks current school/course authority on each read/send, so revoke the actual enrollment or school membership to end required-group access. Optional group joins never extend those grants. Human School/Admin reviews exact AI post proposals; ordinary Teachers cannot approve publication. Do not add native Core participants to application-owned rooms, which would introduce an access path outside school ACLs.

Monitor pending/uncertain chat commands and withheld upstream-message counts. Check a lost send's protected receipt before an explicit original-command retry. Never replace an ambiguous command or replay it under a different actor/key. Disabled chat leaves groups pending; after a known unsent/rejected attempt, an authorized manager can explicitly connect. Uncertain room creation requires operator reconciliation because Core supplies no idempotent create or sole-participant ownership proof; title/topic matches are unsafe and are not adopted. Keep chat disabled during investigation if ownership is in doubt. See [the group runbook](group-chat.md).

Core hostname changes use the [operator issuer migration](core-issuer-migration.md). Export authoritative subject UUIDs, review a no-write plan, stop admission and apply aliases with the reviewed digest. Never create another local user or rewrite coursework/audit ownership to compensate for an issuer change.

Monitor API readiness, Core introspection failures, expired sign-ins, denied assistance, unresolved sends, database storage/backup status and independently retained checkpoint age. Readiness verifies application storage/schema; it does not establish provider availability or current Core permissions. Avoid health probes that consume model tokens.

Back up PostgreSQL and retain its matching encryption bootstrap separately. Encrypt backups and restrict restore/export access. Test restore on a new isolated database using synthetic records and verify the externally trusted audit head before production acceptance. A lost encryption bootstrap makes stored credentials/tokens unavailable; replacing it is not a transparent rotation.

On Core/provider outage, keep coursework evidence intact and retry only a user-visible operation known not to have sent inference. An uncertain send stays uncertain and does not automatically incur a second call. Operator incident response and retention/deletion procedures must be agreed before real student enrollment.

## External review operations

Assign the school reviewer, import existing public course teaching sources, review/publish exact copies, then refresh/approve the corpus and reapprove the class teacher profile. Correct source or policy findings before retrying with a new explicit review identity; never automatically resend an uncertain pending job. A disabled agent, changed model/class/source, negative newer review or expired decision withholds material. Update a video submission to capture changed metadata, then review it again. YouTube visual/audio suitability and applicable site designation require operator/human verification. Revocation blocks future current checks; it cannot recall an already displayed third-party player. See [external media review](external-media-review.md).

## Homework Help and optional voice

For generative Homework Help, a human School/Admin uses **Homework Help AI** in school/administrative settings to save and approve the exact assistant behavior, three school model selections, image policy and limits. Human-taught courses and general study questions need no separate AI teacher assignment. The global live-model gate stays independent. Recheck connection/configuration approval after edits. This feature uses its own student history, daily budgets and phase evidence; the legacy approved-excerpt operation below retains its existing behavior.

School/Admin review includes full school AI conversations. Teachers use **Student sessions → class AI conversations** for their currently assigned class only; general questions and complete provider prompts are excluded. A pending request is never automatically resent. After inspecting current phase evidence, a human School/Admin can use **Close uncertain request** with a required reason and exact reviewed snapshot. This seals a withheld outcome without another model call and releases the pending barrier. A stale snapshot must be reloaded; late active model results are preserved privately as immutable receipts and cannot reopen the request. Preserve its send markers and reservations when reconciling provider billing.

Monitor Core metadata backlog and the independently retained archive separately. The settings card reads saved metadata-delivery counts/timestamps; it does not prove a worker is running. Use the dispatcher's database health check and the archive freshness/failed-Job/checkpoint alerts described in [audit delivery and automatic archive operations](audit-delivery.md). Follow the final owner reconciliation step after old API tasks stop during a rolling release. Neither worker retry authorizes a model resend. Both deployment examples remain suspended pending real storage, keys, credentials and recovery acceptance. Voice for generated replies remains deferred.

Review complete Homework conversations through Student sessions as a current human School/Admin; pre-triage messages and private photo evidence are discoverable separately from course sessions. Course teachers retain their class-specific lesson history, while administrative review links to course/voice evidence. Review reads and photo/audio access are audited. Monitor the independent Homework message/photo-storage limits as well as shared tutoring budgets. A saved message interrupted before lesson admission can be explicitly resumed with its original stored lesson key; never replace an uncertain sent provider request with a new key.

Voice is disabled until a school configures an encrypted provider key, approved stock choices, data handling and limits under the deployment live-model gate. Student recordings are not persisted. Keep the stable vault bootstrap for generated playback as well as existing photo/connection secrets. For unresolved speech operations, inspect durable markers/receipts and reconcile provider state before any manual remediation; no automated reset/retry is provided. Verify catalog account access and its retirement deadline before release and monitor failures; an unavailable stock voice must never fall back to the owner's clone. See [voice operations](homework-voice.md).
