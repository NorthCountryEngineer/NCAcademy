# Teacher onboarding and course knowledge

AI teachers have a separate **Models** workspace for assigning integrated school models. Saving/swapping/approving a model policy preserves the exact teacher personality, profile approval, class assignments and knowledge corpus. Fixed-primary execution and no-call routing previews are implemented; automatic cost-aware switching is planned. See [teacher model settings and implementation plan](teacher-models.md).

Teacher onboarding and corpora are part of the released October 18, 2026 baseline. The current local source extends them with school-wide curriculum setup, grade/year course planning and visible corpus-build receipts; its production release still requires a matching image and exact-source checks. See [school setup](school-onboarding.md).

## Onboard a human or AI teacher

A human Admin or School administrator opens **Teachers** in the selected school and chooses human or AI. Both use the same normal form: portrait, name, biography, title, pronouns, contact email and expertise. AI teachers also have a structured teaching approach: tone, teaching style, amount of detail, question frequency, encouragement and additional boundaries. AI profiles also accept bounded advisory teaching instructions and can remain unassigned base personas. These settings guide teaching style inside the enforced policy; biography, instructions or behavior text cannot replace that policy.

The photo picker accepts local PNG/JPEG/WebP photographs and converts them to a small PNG portrait. The API independently validates dimensions, scanlines, checksums, decompression and size, strips optional metadata and stores only normalized PNG bytes. It never downloads a portrait URL. Contact email is private administrative metadata and is not an account-matching key.

An unbound human profile can be saved while the person completes normal Core account onboarding. An administrator explicitly selects the existing school Teacher account when available. An AI profile normally works as an application-managed tutoring persona: it has no Core identity, Teacher API permissions or credentials. Advanced external-agent access can link the profile once to an existing approved Core agent placement. Profile identity and kind remain stable. A different account requires a different profile; names and email addresses never transfer existing identity or coursework.

Creating a profile does not create an upstream Core account, issue credentials, send an invitation/email or grant permissions. School membership, actual class enrollment/ownership, Core capability checks and agent admission are independent controls. The UI shows the distinction between planned classes and effective teaching authority. Human profile approval is not a substitute for the person's Core account onboarding; AI profile creation is not a deployment-wide agent-enable switch.

## Reuse a personality across classes and grades

A profile belongs to one school and has any number of planned class assignments. For example, the same AI teacher can have a Grade 10 environmental-science class and another class in a different grade. Each class carries its own curriculum and corpus. Updating one class does not create a different teacher personality or change another class's knowledge context.

The teacher retains a stable ID, while edits increment its version. In **Readiness → Profile review**, review the profile, check **I reviewed this teacher profile**, and select **Approve current profile**. Profile review is available even when assigned classes have pending or unsupported teaching corpora. It records an immutable revision of the metadata and exact current planned class references; it does not approve those materials, activate an agent or enable Lesson Q&A.

Updates, binding changes and assignment changes invalidate the current approval while keeping earlier revisions. A later course/resource/catalog change also prevents the old context being used. The manager's approval indicator measures whether those exact references still match, independently of teaching readiness. Each class still needs its own current approved teaching corpus before class tutoring. After approving an updated class corpus, approve the current teacher profile again to capture it; no metadata edit or reassignment is needed. Concurrent edits require reloading after a version conflict.

## Configure a class and build its corpus

The class form records state, subject, grade(s), academic year and an optional standards version. Creating/configuring the class, or assigning the teacher to it, automatically assembles an immutable corpus from the installed reviewed jurisdiction package and scoped class teaching resources. Refresh imports the installed package and current materials; it does not follow arbitrary document links or silently scrape the web on a student request.

The New York **2026–2027 planning catalog covers Pre-K–12** across academic subjects, including theoretical arts and career studies. These framework/topic reviews support school setup and class context; they do not supply complete per-standard mappings or approved teaching libraries. A class with only a framework review receives an unverified corpus with visible alignment/material gaps. It cannot be approved merely because standards links are present. See the [all-subject review](ny-curriculum-2026-review.md).

The exact teaching adapters still cover **US-NY / environmental_science or earth_space_science / high school grades 9–12 / 2026–2027**. The Earth and Space Sciences package supplies 14 selected alignment records and five original public teaching summaries; see [its source review](ny-school-curriculum-sources.md). New York's science standards are a high-school grade band, not a separate state-authored Grade 10 environmental-science syllabus. The class-to-standard mapping is local and explicitly partial. The standards version, mapping version, applicability school year and source-review dates are independent fields. A new school year does not imply that New York adopted new standards.

The starter package automatically supplies 13 mapped standard records and four original teaching summaries drawn from NASA, NOAA and EPA sources. It records source titles, canonical URLs, exact fetched-byte SHA256, retrieval/review dates, standard codes and source pages. Structured summaries have their own hashes and are labeled as summaries. Teaching documents and school-authored supplements retain separate provenance; they are not relabeled as state standards. The class review panel shows the selected sources, documents, coverage and remaining gaps. A source package supplies a teaching reference corpus, not a complete guaranteed curriculum or a claim that a model is an expert.

Authoritative New York references:

- [NYSED Science](https://www.nysed.gov/standards-instruction/science)
- [New York State High School Science Learning Standards](https://www.nysed.gov/sites/default/files/programs/curriculum-instruction/hs-science-learning-standards.pdf)
- [NYSED High School Sciences](https://www.nysed.gov/state-assessment/high-school-sciences)

Unsupported states, subjects, grades, school years, standards versions or expired source reviews remain **unverified** and cannot be approved for teaching. The application reports that gap rather than choosing an unrelated standard or inventing a current-year claim.

## Review and retrieval

A human School/Admin reviews the exact corpus and acknowledges its coverage before approval. Approval binds the corpus ID, snapshot hash, course configuration and catalog/resource hashes. Refresh creates or reuses a content-addressed snapshot; it never edits historical versions. Currentness is recomputed from saved course metadata, installed catalog bytes and current scoped text resources, so changing or deleting a resource invalidates the old approval immediately.

Assigned human and Core agent Teachers can retrieve evidence from their authorized class's approved current corpus. The initial retrieval algorithm ranks bounded token overlap and returns exact quoted excerpts with document IDs, content hashes, positions and source citations. No matches means no evidence. It makes no inference or arbitrary tool call. Every retrieval records its actual query, selected evidence and provenance in the audit chain. Teacher-only resources remain inside authorized teaching contexts; the corpus review/retrieval API is not a public student document endpoint.

Adding a state/subject requires a reviewed JSON source package, validated mappings/applicability and registration in `CATALOG_PATHS` in `academy/standards.py`. The catalog-driven UI then uses that package without a separate state-specific onboarding form. Multiple packages can cover different years or mapping versions. Selection matches the entire class configuration within one package, chooses its most recent valid review and rejects unresolved ambiguity. Catalog responses group subjects and expose exact per-version applicability; an unrelated catalog addition does not invalidate existing approved classes. Reviews must validate authoritative source bytes, rights, standards codes, grade bands, effective dates and mapping gaps; the package's academic-year allowlist is not an automatic currency certificate.

## Automatic Lesson Q&A and publication policy

The confirmed policy permits automatic tutoring inside a human-approved behavior profile and course corpus. Assignments, lesson materials and feedback still require human publication approval. The teacher form includes an explicit Lesson Q&A model policy: a named enabled connection, approved model, daily request/token reservation caps, question size and output-token limit. Approval captures those settings together with the profile and each approved class corpus. An unconfigured model policy keeps Lesson Q&A unavailable.

Lesson Q&A is a separate course activity from assessed work. An enrolled student chooses an available approved AI teacher, asks a question and receives an exact reviewed public-source excerpt with a citation and bounded fixed teaching-style prompts. The model selects an admitted passage ID; it cannot write the displayed explanation. Only current approved public source-reference documents or explicitly student-visible supplements can supply passages. Standards summaries and teacher-only resources cannot become student-visible answers through corpus approval alone. Obvious essay/completion requests are blocked before inference. No student draft, essay-writing tool, submission action, arbitrary tool or provider-generated prose is part of this activity. This initial extractive implementation does not provide unrestricted conversational explanations.

The server resolves the profile/course/model itself, records exact immutable context and candidate passages, reserves capacity and commits a send marker before inference. It revalidates student enrollment, approvals, corpus, connection and deployment gates before sending and before release. A managed persona needs the global live-model gate. A Core-bound teacher additionally needs actual class teaching authority, active local placement, agent admission and independent fresh Core authorization; revocation never changes it back into a managed persona. Stale approval, absent evidence and disabled gates block the request.

Daily request and conservative UTF-8 prompt-byte/output-token reservation limits are shared across all teacher profiles for each student and class, resetting at midnight UTC. Changing teachers cannot reset the quota; the stricter policy encountered during that day continues to apply. Token reservations are not dollar budgets or provider tokenizer guarantees. Full course history remains available after the daily reset. Any unresolved pending request blocks new sends across days. The same idempotency key replays the recorded result without another call; ambiguous sends are never automatically retried.

Assignment tutoring retains the student-attempt requirement and instructor-approved question/hint ID boundary. Its optional named teacher context uses a Core-bound profile and the same currentness/revocation checks. A model cannot write or submit student work in either activity.

Students may additionally ask this teacher to assemble a private multimedia lesson from a task description or bounded assignment photos. This has separate curation/image policy opt-ins and uses the same approved public course context, source/visual ID boundary, daily quota and audited send/release lifecycle. The private lesson can include interactive source-linked diagrams, browser read-aloud and recorded student reflections; it does not publish new class materials. See [student-curated lessons](student-curated-lessons.md).

Normal student turn responses contain safe teacher metadata, their own question, release outcome and citations. Private contact information, prompt/context snapshots and binding details remain restricted. Authorized session replay distinguishes Lesson Q&A from assignment tutoring and includes exact profile revisions, corpus references, admitted excerpts, prompt, visible provider selection, usage, reservations and authorization/release evidence. Reviewer reads and scoped exports are audited. Hidden model reasoning is never collected.

## Persistence, migration and release

Profiles, planned assignments and current approval pointers use scoped `Record` rows. Teacher profile revisions, course corpus snapshots and corpus approvals are append-only records. Pending model turns can advance through send and completion; terminal assignment/lesson turns cannot be rewritten or deleted. Schema 3 enforces these rules in the ORM and SQLite/PostgreSQL triggers and appends an audit receipt without rewriting old identities, records or audit events. The API's restricted database login retains its existing privilege boundary. Current readiness requires all explicit markers through schema 7; the additive school-onboarding revision protects curriculum and knowledge-workflow evidence. Startup/login never migrates the database.

Run the owner migration before activating the new API image. Keep the existing session bootstrap, Core registrations, canonical issuer, service credentials and audit archive unchanged. Live models and agent admission remain explicit deployment gates, with no new credentials or grants issued by this feature. The local release manifest intentionally contains `REQUIRES_IMMUTABLE_PRIVATE_ECR_DIGEST` until this changed API is published; the previous production image cannot serve these new endpoints.

Core-bound selected-teacher tutoring additionally requires the separate [binding-authorization supplement](../nce/teacher-binding-authorization.patch), reviewed against Core `e6eb31f3caed491445e2582e34b8da43b3556d97`. Its read-only `/api/platform/v1/agent-bindings/authorize/` endpoint authorizes an existing binding under its own installation workload credential and current roles/resource/task/environment policy. It issues no agent credentials. The [baseline receipt](../nce/teacher-binding-authorization-baseline.json) records the exact hash and offline test scope. Apply it through Core's normal reviewed release; the active Core checkout and production service were not changed. A missing endpoint fails closed. Managed-persona Lesson Q&A does not require this supplement.

Synthetic tests and a separate local container preview exercise onboarding, multi-class assignments, snapshot approval, stale/revoked context, source evidence and historical audit preservation. See [verification](verification.md) for the actual completed checks. Production acceptance, fresh owner UI checks and a new retained audit checkpoint are separate from local implementation.
